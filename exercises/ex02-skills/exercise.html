Exercise 2 · Day 1 · Extension layer

Skills: package the procedure, prove it fires 🧩

🎯 Objective

Ledgerly's PR notes follow a house format: six sections, the ADRs the change touches, and a verification table that matches reality. That's a procedure, not a fact, so it doesn't belong in CLAUDE.md. Watch the agent write a generic note, then package the procedure as a skill with a description that fires it, a script it runs and a template it reads only when needed. Finish by turning a second skill into a sandboxed, forked worker. Each step is graded by a check the agent can't see.

🗂️

Build a skill folder: SKILL.md, a reference.md loaded on demand, a script that's run, not read.

📝

Write a description + when_to_use that fire the skill without naming it, and not on everything else.

⚡

Pre-fill a skill with !`command` dynamic context and ${CLAUDE_SKILL_DIR}.

🛡️

Use allowed-tools as a sandbox: it pre-approves and forbids.

🍴

Move work off your context with context: fork · agent · model · effort.

✍️ Author ship-check: description first

7 min

Create the folder, copy the gates script in, then write two files yourself: SKILL.md (frontmatter + a short body) and reference.md (the PR template and the path → ADR map). The house headings are Ticket · Summary · ADRs touched · Verification · Risk & rollback · Changelog.

▶ Scaffold

mkdir -p ledgerly/.claude/skills/ship-check/scripts cp exercises/ex02-skills/starter/gates.py ledgerly/.claude/skills/ship-check/scripts/ # now write SKILL.md and reference.md in ledgerly/.claude/skills/ship-check/

.claude/skills/ship-check/ ├─ SKILL.md # name · description · when_to_use · argument-hint · allowed-tools + body ├─ reference.md # PR template + path → ADR map · loaded only when the body says "read it" └─ scripts/ └─ gates.py # runs the 4 gates, prints a table · run, never loaded
▶ Lint it before you trust it

python3 tools/skill_lint.py ship-check --profile ship-check

WhyThe description is the only part Claude sees before choosing: write it first. The body pulls the diff and the gate results in with !`…` lines before Claude reads it, and points at reference.md so the template costs nothing until it's needed. allowed-tools pre-approves the commands it runs and forbids the rest, so this skill can write a note but can't touch code.

✅ Acceptance criteria
skill_lint.py … --profile ship-check prints GREEN (18 checks).
when_to_use lists 3+ phrasings people actually type.
allowed-tools has no bare Bash and no Edit.
💡 Stuck? Hints unlock in order
1 · nudgeWhat goes in the frontmatter?
What it does (third person) · when to use it, in the words your team types · what to pass · which tools. The linter's failure lines say exactly which field is missing.
2 · specificThe body, in four lines
Dynamic context: !`git status --short`, !`git diff HEAD --stat`, !`python3 ${CLAUDE_SKILL_DIR}/scripts/gates.py`. Then: read reference.md · copy the gate table into Verification unchanged · never claim a gate passed unless the table says so · write to docs/pr/<ticket>.md.

🎯 Trigger it by name

3 min · green
▶ Fresh start, fresh session

tools/start.sh led-120 && cd ledgerly && claude

▶ Type in the chat

/ship-check LED-105

▶ /exit, then

cd .. && tools/check.sh led-120 --label by-name

WhyThe folder name is the command. Calling it by name proves the body works: the dynamic context ran, the template was read, and the verification table is real. The checker re-runs every gate, so a note that says "pass" for a failing gate stays red.

✅ Acceptance criteria
/ship-check appears in the / picker with your argument-hint.
tools/check.sh led-120 → GREEN on all four checks.
💡 Stuck? Hints unlock in order
1 · nudge/ship-check isn't in the picker
Skills load at session start. Did you start a new session after writing it? Is the path exactly ledgerly/.claude/skills/ship-check/SKILL.md?
2 · specificIt's listed but errors / looks empty
Run the linter again: broken YAML (first line not exactly ---, tabs) or a missing linked file are the usual causes. claude --debug shows the skill loading.
3 · near-completehonest-verification is red
The note's Verification must name all four gates, each with pass or fail, matching a re-run. Make the body say: "Copy the gate results table into Verification unchanged." The table comes from gates.py, so the agent has nothing to make up.

🪄 Make it fire without its name, and only then

5 min · red → green

Two fresh sessions. The first should fire ship-check without you naming it. The second is a plain question and should not fire anything. The checker reads your transcript for a Skill call.

▶ A · should fire

tools/start.sh trigger-implicit && cd ledgerly && claude # paste the prompt below, /exit, then: cd .. && tools/check.sh trigger-implicit

▶ A · paste (don't name the skill)

LED-105 is done on this branch. Can you make it reviewable?

▶ B · should stay quiet

tools/start.sh trigger-quiet && cd ledgerly && claude # paste the prompt below, /exit, then: cd .. && tools/check.sh trigger-quiet

▶ B · paste

Quick question, no changes please: how does fx.convert round amounts, and why that way?

WhyClaude picks skills by reasoning over descriptions, not keyword matching. "Won't fire" means the description is too vague or uses words nobody types. "Fires when it shouldn't" means it's too broad. The lecture's test is three prompts that should trigger it and one that shouldn't. This is that test with a grader.

✅ Acceptance criteria
tools/check.sh trigger-implicit → skill-fired PASS, and the note is green again.
tools/check.sh trigger-quiet → both skills stayed quiet, no files written.
Measure it: tools/run_drill.sh trigger-implicit current 3 gives you a firing rate.
💡 Stuck? Hints unlock in order
1 · nudgeIt didn't fire
Say it out loud: do the words in prompt A appear in your description or when_to_use? "Reviewable" won't match "review-ready" in every run.
2 · specificIt fired on the question too
The description is claiming the whole repo ("helps with Ledgerly changes"). Narrow it to the job: preparing a change for review, and list the moments: before opening a PR, asked for a PR note, "is this ready to ship".
3 · near-completeA when_to_use that does both

⚙️ Advanced: turn a skill into a sandboxed worker

6 min

Author a second skill, adr-audit, that reviews the diff against docs/decisions/ and physically can't edit. Then move it off your main context with the four worker fields.

▶ The frontmatter fields to use

allowed-tools: Read, Grep, Glob, Bash(git diff:*) # read-only sandbox context: fork # its own window: only the findings come back agent: Explore # hand it to a specific subagent model: haiku # a cheap tier for a mechanical sweep effort: low # don't overthink a first pass

▶ Lint, then run it

python3 tools/skill_lint.py adr-audit --profile adr-audit tools/start.sh led-120 && cd ledgerly && claude # /context → note the token count # /adr-audit → then /context again # then type: "now fix the first finding yourself, from inside the audit"

Try thisWhat to noticeYour note
with context: forkOnly the findings land in your windowΔ tokens: ____
remove context: fork, re-runEvery file it read now stays in your contextΔ tokens: ____
"fix the first finding"The audit can't write: Write isn't allowedrefused? ____
effort: low → highSlower, more thoroughworth it? ____

Whyallowed-tools turns "please don't edit" into "can't edit". context: fork plus agent, model and effort turn an instruction into a worker with its own settings: a cheap model on low effort for a mechanical sweep, and your window gets the answer, not the 40 tool calls that produced it.

✅ Acceptance criteria
skill_lint.py adr-audit --profile adr-audit → GREEN.
Your /context grew by less with fork than without (fill in the table).
Asked to fix from inside the audit, it reports the fix instead of making it.
💡 Stuck? Hints unlock in order
1 · nudgeLint says "not read-only"
Only Read, Grep, Glob and git read commands are allowed. Bash on its own, Write or Edit each break the sandbox.
2 · specificThe main agent fixed it anyway
That's a real finding. The sandbox applies to the skill's run. When the forked audit returns, your main session still has its own tools. To make "can't edit tests/" hold for everyone, you need a hook: Exercise 3.

📊 Evaluate the skill like a feature

homework · ~10 min of your time

Step 3 was one prompt each way. Before you trust a skill, run an eval set: four prompts that should fire it, three that shouldn't, each 3 times, plus a baseline with the skill removed. The eval file is exercises/ex02-skills/evals/ship-check.json. Add your own phrasings to it.

▶ Run it (headless, uses your current memory files)

python3 tools/skill_eval.py exercises/ex02-skills/evals/ship-check.json --quick # 2 runs, a smoke test python3 tools/skill_eval.py exercises/ex02-skills/evals/ship-check.json --runs 3 --baseline # the real eval, ~33 runs

metric value target trigger recall (fires when it should) 11/12 · 91% ≥ 80% false fires (fires when it shouldn't) 1/9 · 11% 0% output quality WITH the skill 10/12 · 83% ≥ 80% output quality WITHOUT it (baseline) 0/12 · 0% lower than with Verdict: sharpen it 🔁 ← example numbers; yours will vary

WhyThe lecture's rule: baseline with vs. without before you trust it, and test it like a feature. Four numbers tell you what to fix. Low recall: add phrasings. False fires: narrow the description. Fires but low quality: fix the body, template or script. No gap against the baseline: the skill isn't earning its tokens. The report is saved to runs/skill-eval/ship-check/report.md.

✅ Acceptance criteria
Recall ≥ 80%, false fires 0, quality with the skill ≥ 80%.
The baseline is clearly lower than with the skill.
You added one prompt of your own to each list, and the verdict still says ship it.
💡 Stuck? Hints unlock in order
1 · nudgeIt takes too long
Each run is a full headless agent session. Use --quick while iterating on the description, and the full run once, before you commit the skill.
2 · specificOne should-fire prompt keeps missing
Open its transcript in runs/skill-eval/ship-check/should-*.jsonl. Did the agent do the job without the skill? Then the description doesn't connect that phrasing to this job. Add the phrase itself to when_to_use.
3 · near-completeThe rename prompt fires it
The description is claiming "changes" in general. Tie it to the review moment: "Prepares a change for review … Use when someone wants it ready for review / a PR note / about to open a pull request." Nothing about editing code.
