You finish on the classic trap: a team convention that only lives in your home directory.

📏

🔍

📏 Move testing conventions into .claude/rules/

4 min

Create ledgerly/.claude/rules/testing.md with at least three test conventions for Ledgerly: naming, which fixtures to use, how to assert money, and what to do when an existing test contradicts the request.

Why.claude/rules/ holds topic files instead of one monolithic CLAUDE.md. Without frontmatter a rule loads every session, at the same cost as CLAUDE.md. Add paths: and it loads only when matching files are touched. That's the whole of Exercise 2.

✅ Acceptance criteria
.claude/rules/testing.md exists with three or more test conventions.
/context at the root lists it under Memory files.
Stretch: add paths: ["tests/**"] frontmatter and watch it disappear from /context until a test file is read.
💡 Stuck? Hints unlock in order
1 · nudgeWhere do conventions come from?
Open tests/conftest.py and ruff.toml. The fixtures and the PT lint rules are your raw material.
2 · specificFour candidates
Name tests test_<behaviour> · use the conn / client / paid_invoice fixtures · assert money as Money or *_cents, never floats · never change an existing assertion to make a test pass.
3 · near-completeShow me the file 
# Testing conventions
- Run with `uv run pytest -q`. `landmine` tests are deselected on purpose.
- Name tests test_<behaviour>, one behaviour per test.
- Use fixtures from tests/conftest.py: conn, client, paid_invoice.
- Assert money as Money or integer *_cents, never floats.
- pytest.raises always takes match= (ruff PT011).
- Never change an existing assertion to make a test pass.
  If an existing test contradicts the request, stop and say so.

🔗 Import a shared standards file with @

4 min

Create ledgerly/docs/standards/api-conventions.md with Ledgerly's API conventions, including RFC 9457 problem+json errors. Then add one line to your project CLAUDE.md:

▶ Add this line to ledgerly/CLAUDE.md

@docs/standards/api-conventions.md

▶ Measure what it costs

python3 tools/memory_size.py # from the workshop root: follows @imports

Why@ imports make standards modular: one file, imported by whichever CLAUDE.md needs it. But imports load eagerly, at session start. Splitting a file up organises it. It doesn't make it cheaper.

✅ Acceptance criteria
Your project CLAUDE.md has a line beginning with @ that points at the standards file.
docs/standards/api-conventions.md exists and includes the problem+json rule.
/context (new session) shows the imported content loaded; memory_size.py total includes it.
💡 Stuck? Hints unlock in order
1 · nudgeThe import isn't showing up
The @ must start the line, with nothing else on it, and the path is relative to the file containing it.
2 · specificWhat goes in the standards file
Path naming (plural, kebab-case), amounts as integer *_cents plus currency, and the error shape: application/problem+json with type, title, status, detail.
3 · near-completeShow me the file 
## API conventions
- Paths are plural nouns, kebab-case: /invoices/{id}/refunds.
- Amounts are integers named *_cents, with a separate currency field.
- Every error is RFC 9457 problem details: content type
  application/problem+json, body {"type","title","status","detail"}.
- Map domain exceptions to problems in one place (api/errors.py).

🏛️ The hierarchy you're building
👤
~/.claude/CLAUDE.md
User. You, every project. Not in git.
📜
./CLAUDE.md · .claude/CLAUDE.md
Project. The whole team, via git. Loads at start.
🔗
@docs/standards/…md
Import. Inlined eagerly into the file that imports it.
📏
.claude/rules/*.md
Rules. Always, or only on paths: match.
📁
src/**/CLAUDE.md
Directory. Lazy: when Claude works in that folder.
🏠
CLAUDE.local.md
Local. You, this repo, git-ignored.
⚠️
Green tests ≠ no drift
Step 0 passes pytest, ruff and import-linter, and it's still wrong. That's why there's a drift checker.
⚖️ Concatenated, not overridden

Every loaded memory file is concatenated. No "more specific wins". When two disagree, the model picks one, and maybe a different one next run.

Strict precedence exists only in settings.json (managed › local › project › user).

🧭

Write what the code can't say

Commands, the finish line, which code is legacy, where decisions live. Not style rules a linter already enforces.

🏛️

Scope is part of the rule

Team rules go in project. Package facts go in directory. Preferences go in user. A correct rule at the wrong level is a missing rule for half the team.

📏

Measure in rates

Agents vary. One green run proves nothing. run_drill.sh … 3 turns "it worked" into "3 out of 3".
